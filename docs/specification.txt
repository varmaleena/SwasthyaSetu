01 / The prototype we are committing to
Build a working online demonstration of SwasthyaSetu: an AI-assisted system that anticipates medicine
shortages, identifies a facility that can safely share stock, and tracks the approved transfer through
receipt. The central demonstration must answer: Why this recipient, why this supplier, how much, and
what happened after approval?
This plan is self-contained and supersedes the earlier blueprint's cloud-service choices for the submission
prototype. It preserves the important product workflows but substitutes free infrastructure. The earlier
blueprint remains a longer-term reference, not a claim that Vertex AI, Cloud SQL or a national deployment
has been implemented.
Scope and truthful claims
MUST: actual database writes, live Google AI extraction, a trained numerical forecast, computed transfer
recommendations, role-scoped actions, receipt reconciliation, bed/personnel/footfall views, multilingual
reporting, offline drafts and a real small shared-model round.
Use fictional facilities and generated operational records, labelled on every relevant screen. Physical
delivery, actual government data integration, medical policy validation and national operating capacity
are outside the submission. Simulated actors carry out real application state transitions; no physical
medicine shipment is implied.
Existing software already supports inventory and redistribution. Our testable distinction is accounting for
demand hidden by stock-outs, protecting the supplying facility, and connecting the decision to verified
receipt. Improvement must be measured, not asserted.
What the judges receive
A publicly reachable application, public source repository, 3-5 minute video, 10-12 slide pitch PDF under 5
MB, and a short solution description. The application must work without the developer's laptop, personal
login, local tunnel or live assistance.
One clear story is the centre of the video. Additional screens remain independently usable so judges can
inspect the full challenge coverage. A recorded video supports the application; it does not replace it.
Status of this document
Version 2.0 - Submission Build Plan, 27 September 2026. This is an implementation plan, not completed
software. All limits and acceptance targets below are proposed engineering defaults. Confirm free-tier
eligibility and model access in the actual accounts before deployment. No guaranteed uptime, selection or
win is promised.

Trust boundaries and actual isolation
The public PWA calls one hosted API over HTTPS. The API contains State A and State B node adapters,
each with separate database credentials. The shared-model coordinator is a separate module that accepts
parameter updates and aggregate metrics, not raw rows. This is database-separated federation in a
shared demo runtime, not independently administered state infrastructure.
The same node interfaces MUST also run as separate local processes through Docker Compose. An
automated integration test records a real exchange between them. Public judges can trigger the
lightweight hosted round; they do not need to run Docker.
Operational data and evidence are stored in Supabase. A trusted, versioned model artefact ships with the
backend image. Nothing important depends on Render's writable disk. Read-only seed templates ship with
the repository. Restarting the backend must preserve visitor progress.
The API enforces sessions, scope, quantity validation and audit rules. Gemini returns drafts only. A
numerical model produces forecasts. OR-Tools computes allocations. A separate verifier checks them
before any stock reservation. Frontend explanations use verified numeric values.

04 / Accounts, setup and ownership
checklist
Prepare these accounts
Use GitHub for a public repository; a Google account for Firebase Hosting and Gemini API access; Render
for the API; and Supabase for two free database projects. Use one team-owned project set with
documented ownership. Do not create extra accounts to evade free limits. If the account cannot create
two free projects, resolve that before claiming separate databases.
Setup order
1. Create a public repository with a licence, README and empty issue/backlog list. Turn on available secret
scanning and protect the release branch where feasible.
2. Create Supabase State A and State B projects. Save database connection settings privately. Create an
application database role with only required table permissions. Apply the same migrations to both.
3. Create a private evidence bucket in each project. Deny unauthorised public access. Backend
upload/download operations must verify session ownership first.
4. In Google AI Studio, create the API key for an eligible free-tier project. Test a small text, image and
audio request using the chosen model. Record model ID, quota, date and observed latency.
5. Create one Render Free web service connected to the repository. Add secrets through its dashboard,
not GitHub files. Deploy the API, connect both databases, and test readiness.
6. Create a Firebase project on Spark. Initialise Hosting for the web build folder. Configure SPA rewrites
and deploy the static site. This is Firebase Hosting, not Firebase App Hosting.
7. Set the frontend API origin and backend allowed origins to the actual deployed HTTPS URLs. Verify
browser access in an incognito window.
Secret placement
Server-only: GEMINI_API_KEY, STATE_A_DATABASE_URL, STATE_B_DATABASE_URL, state storage
credentials, DEMO_TOKEN_SECRET and owner identity settings. Public frontend configuration: API base
URL and build version only. Never place server secrets in VITE_* variables.
Store project IDs, URLs and setup notes in docs/DEPLOYMENT.md without keys/passwords. Keep
.env.example with names and placeholders. Rotate any exposed secret before continuing. The owner
performs authenticated account creation; coding agents should not invent credentials or claim
provisioning succeeded without evidence.

05 / Judge access and independent demo
sessions
Landing experience
The public URL opens a static page immediately, even when the API sleeps. Explain the product in one
sentence and show Start interactive demo, Watch walkthrough, and View source. Mark the environment as
a synthetic prototype. The video link is useful during an outage but is not a replacement for the interactive
button.
On Start, call readiness. If the backend is waking, show a plain progress message and bounded retry. After
an initial waiting window, offer Retry and Watch walkthrough; do not leave an infinite spinner. The
developer must test this from a genuinely idle deployment.
Session design
POST /api/v1/demo/sessions creates a random, expiring sandbox. Return a signed token bound to
session_id and allowed demo permissions. A judge does not need registration, email verification or shared
administrator credentials. Keep the token in session storage and enforce a restrictive content-security
policy to reduce exposure.
All mutable demo rows include session_id plus state_id. Use shared immutable historical seed data and
small session-specific operational copies. Each visitor sees their own approvals, receipts and reset. Never
reset the global seed dataset when a judge presses Restart.
Default session expiry: 24 hours, with a visible restart option. Store progress remotely so browser refresh
and backend restart do not lose it. Rate-limit session creation and AI usage. When the cap is reached,
explain the limit; do not create unbounded data.
Role simulation without pretending to be officials
The walkthrough offers Switch demo role among facility custodian, district planner, district approver and
receiver. Every action still checks role/scope and logs the simulated actor. Label this as role simulation in
an isolated sandbox. It is not evidence of independently authenticated real officers.
Owner-only functions such as global model publication or data deletion require a separate authenticated
owner identity. Guest tokens must never authorise those functions. If genuine multi-user accounts are
later added, keep that authentication separate from judge convenience controls.
Cleanup can run in bounded chunks on owner invocation or legitimate requests, deleting expired session
data only. No paid scheduler is needed. Do not keep services artificially awake to defeat free-tier policies.

Input options
Provide four working paths: manual entry, CSV import, stock-card photo and short recorded voice report.
Include downloadable fictional sample CSV/images/audio on the demo page. Judges must be able to test
without photographing a real pharmacy record.
For CSV, distinguish a stock snapshot from a movement. A snapshot proposes reconciliation; it must never
be added as a receipt. Preview row-level validation failures, catalogue mappings and conversions. Invalid
rows remain uncommitted until fixed. Reconcile snapshots as of observed_at and account for later
movements; if timing is ambiguous, request a recount rather than overwrite the current balance.
Google AI path
Upload to private storage, validate size/type, call Gemini, validate its JSON and present a confirmation
screen. Original product wording, quantity, unit, batch and expiry appear beside extracted fields. Missing
values remain null. Exact strength, formulation and pack size require a catalogue match. The user
confirms before the API creates a stock adjustment.
Audio uses browser recording over HTTPS and an audio-capable model verified in setup. Hindi and Telugu
clips must be tested, not assumed. Provide typed input if the browser cannot record or the quota is
exhausted. Reviewed interface translations are separate from model transcription.

08 / Forecasting that runs on a free
prototype
What is learned
Forecast daily requested units for each exact medicine/facility. Dispensing on an out-of-stock day is a
censored observation; it is not a normal zero-demand day. Keep missing reports, closed facilities,
confirmed zero demand and stock-outs distinct. Footfall, in-stock fraction and recorded unfilled requests
provide context, not perfect ground truth.
Implementation sequence
1. Baseline: recent same-weekday median from valid in-stock days, with a pooled fallback for sparse
history.
2. Stronger baseline: adjust consumption for in-stock days and known utilisation changes.
3. Small advanced model: negative-binomial count regression with shared features and facility/product
effects. Use a censored likelihood only where stock exhaustion is known; preserve ordinary likelihood for
uncensored days. Train locally using CPU and a reproducible script. Avoid large neural runtimes in the
hosted image.
4. Save coefficients, feature schema, calibration parameters, training cutoff and hash as JSON/NPZ. Load
only trusted bundled artefacts; never unpickle user-uploaded models.
5. Hosted inference recomputes forecasts from current session observations. It must not return a
hardcoded shortage because a scenario name matches.
Inputs and uncertainty
Use lagged consumption, in-stock indicators, weekday, footfall and approved aggregate context available
at the cutoff. Start with synthetic delivery lead-time distributions, clearly labelled. Generate 100 seeded
demand/delivery scenarios for the small demo; share district shocks across neighbours. Produce 14-day
risk and p10/p50/p90 summaries. Sum each sample path before computing cumulative quantiles.
If the small advanced model cannot pass evaluation, show the baseline transparently and retain advanced
mode as experimental. Do not claim hidden-demand recovery accuracy without held-out evidence. Google
AI's mandatory contribution remains live Gemini extraction; local training is explicitly not Vertex AI.
Inference and allocation are triggered by confirmed events while the app is active and by an explicit
Refresh analysis button. Display last computation time. A sleeping free backend is not an always-on
emergency-warning service.

09 / Redistribution calculation and golden
test
Use a small OR-Tools integer allocation model. Inputs: exact batches, free usable stock, reservations,
expiry, demand scenarios, arriving replenishments, configured reserve policy and synthetic travel-time
edges. Output includes quantities, reasons, unresolved shortages and solver status.
Hard exclusions: expired/quarantined stock, wrong product or unit, insufficient storage suitability, arrival
too late, duplicate allocation and unauthorised route. A proposed transfer must protect donor demand plus
reserve under the configured scenarios. A numerical verifier independently checks the saved plan.
Demo policy defaults: donor stock becomes stale after 24 scenario hours; capacity after 8 scenario hours;
plans expire after 2 scenario hours; incomplete reservations expire after 30 scenario minutes. Make these
configurable and visible.
Objective order: reduce weighted unmet demand; then reduce unequal shortage burden; then reduce
transport and expiry waste. Weights are visible demo policy, not official clinical priorities. Keep maximum
runtime bounded; return a verified feasible result or a clear timeout/infeasibility message. Never call a
timed-out feasible plan globally optimal.

10 / Approval, dispatch, receipt and error
handling
Operational sequence
Draft plan -> proposed transfer -> donor reservation -> required district approvals -> approved ->
dispatched -> partially received or received -> closed. The receiver and donor are in different districts
within one simulated state. Cross-state shipment is disabled in v1.
Record the requesting district and supplying district approvals separately. The public judge can switch
labelled demo roles, but the server still checks that the active role can perform that step. A missing
approval must block dispatch.
Transaction behaviour
At reservation, lock donor balance rows in stable order. Recheck batch status, available quantity, snapshot
version and plan expiry. Atomically create reservation, transfer event and audit record. A second
competing request must see the updated balance or receive a conflict.
At dispatch, reduce donor on_hand and reserved quantities together; increase in-transit. At receipt,
reduce outstanding transit and increase recipient on_hand. Duplicate commands with the same key return
the original result. The same key with different content returns a conflict. Partial receipt leaves the
remainder in transit.
Before dispatch, cancellation releases reservations. After dispatch, use explicit return/loss/reconciliation
events instead of putting stock back automatically. All adjustments need a reason and actor.
UI failures to implement
Stale plan: show which record changed and offer Recalculate. Expired/quarantined batch: show a hard
block. Backend restart: reload progress from the database. Duplicate click: show the existing result once.
Missing shipment quantity: keep a discrepancy task. No safe donor: display unresolved need and reviewed
escalation.
Expiry is evaluated against the scenario clock for fictional data, clearly labelled. Use a frozen logical date
that advances through demo actions; the scenario must not break when a judge opens it weeks later. Real
wall-clock timestamps still govern session expiry, quota and security. Never use the scenario clock to
bypass authentication expiry.

11 / Beds, attendance, footfall and
federation
Complete challenge coverage
Facility readiness screen: operational beds, occupied beds, free beds, staff present by role, patient footfall
and last update. Implement actual edit/import and persisted refresh. Show unavailable or stale
information distinctly. A bed count alone does not establish staffing or treatment capability.
Use these observations in the story: increasing footfall informs demand; a facility with absent relevant
staff is marked as an operational concern. Medicine transfers remain the deep workflow. Do not add
automatic treatment decisions, patient routing or staff deployment without a defined clinical policy.
Working shared-model demonstration
Both state adapters read their own synthetic training partitions and perform a small update to an identical
shared count model. The coordinator receives only the agreed parameter vector, capped sample count
and aggregate metrics. It validates shape, feature-schema version and finite values, aggregates the
updates, and proposes a new model version.
Each state evaluates the candidate locally and may reject it if validation worsens. Show local-only and
shared-model metrics, training round ID, update hashes and activation decisions. A negative result is valid
evidence; do not force an improvement for the demo.
Use the same model family and feature schema as the main forecasting pipeline, with facility-specific
terms kept local. Bound the demonstration to a small historical subset and one round. Large training
happens offline, not inside a public request.
Hosting truth
Public demo: separate state databases, shared API/runtime, explicitly labelled. Local integration test:
separate processes using the same node contract. This demonstrates working information exchange but
not independent state governance, secure aggregation or formal privacy guarantees. Model updates can
leak information; keep this exercise synthetic.
No national claim is supported merely by showing two state labels. Scaling evidence consists of tested
interfaces, separate datasets, configurable policies, language adaptation and measured workload. A
production federation is a post-selection milestone.

No hidden always-on worker requirement
Fast operations run in the request with strict timeouts. Longer extraction/model rounds use a persistent
job record with checkpoint, lease expiry and idempotent step results. The active client explicitly advances
steps and polls status. An owner can resume the same job later; a process restart cannot lose completed
results.
Use an atomic lease to prevent two clients running the same step. Network failure around an external AI
call can cause a retry and additional quota consumption; record this limitation rather than claiming
exactly-once provider execution. Limit retries.
Do not rely on an in-memory queue, a daemon surviving service sleep, local SQLite or a free background
worker that does not exist. Test the hosted CPU/memory limits and shorten the workload if required,
without replacing computations with canned answers.

17 / Security, quotas and failure recovery
Public demo protection
Only fictional data is accepted for the demonstration. Display this before uploads. Rate-limit session
creation, AI requests and allocation runs, with counters stored in the database. Cap input size, output
tokens, job steps and execution time. Validate extensions and actual media type; reject executable
content.
Session tokens are signed, expiring and scoped. Enforce every permission server-side. Use parameterised
database queries and compound tenant/session keys. Test attempts to substitute another session's
transfer, batch or evidence ID. Private evidence downloads require scoped authorisation.
Free-service constraints and responses
Render's free backend can sleep or restart, and local file changes are not durable. Persistent state belongs
in the database/storage. Keep the frontend independently available, show wake-up status and use
bounded retries. Do not introduce a paid cron or worker as an unnoticed dependency. [S1]
Supabase can pause an inactive free project. Before recording and during the official evaluation window,
the owner checks project status through normal maintenance and restores it if needed. Test the real
application after restoration. Do not promise 24/7 availability. [S2]
Gemini rate limits produce a visible quota message and a manual-entry path; live AI can be retried later.
Preserve already completed stock/transfer steps. A recorded extraction may be offered only in a
separately labelled replay, never as a replacement disguised as live AI. Free-tier data handling differs from
paid services, so exclude real patient/staff records. [S4]
Recovery checklist
API restart: resume session and checkpointed job. Database outage: read-only explanation and Retry; no
fake mutation success. Solver timeout: verified feasible incumbent or no plan. Invalid model response:
validation error and manual correction. Duplicate request: original response. Session expired: clearly start
a new sandbox. Failed receipt: keep stock in transit until resolved.
Protect owner operations with actual identity. Guest role switching authorises only synthetic sandbox
actions. Log trace IDs and structured errors without keys, raw audio or confidential data. Review usage
and deployments as a team; never assume a budget alert alone prevents charges.
